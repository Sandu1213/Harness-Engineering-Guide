# Decisions

## D001：原创实践指南，而非逐字翻译

**背景：** 本书受到 Lilian Weng《Harness Engineering for Self-Improvement》启发，但目标读者需要中国工程语境下的可操作指南。

**决策：** 不制作逐字中文翻译；使用原创章节结构、案例、图示和工程推导。

**原因：** 保护版权、避免误述作者观点，并让内容适配长期变化的工具与工程实践。

**后果：** 每个外部事实都需独立引用；来源观点与本书扩展必须分开标注。

**状态：** 已采纳。

## D002：仓库本身作为 AI 上下文

**背景：** 长期写作不能依赖短暂聊天记录或单一 AI 的记忆。

**决策：** 使用 `.context/`、`.memory/`、`.ai/`、模板和书稿目录作为可读、可 diff 的长期上下文。

**原因：** 新 AI 能在数分钟内恢复项目目标、状态、决策和下一任务；人类也能审查这些信息。

**后果：** 每个任务完成时必须更新状态、进度、必要决策和交接。

**状态：** 已采纳。

## D003：使用 AGENTS.md 与 CLAUDE.md 作为工具入口

**背景：** Codex 与 Claude Code 都会参与，若入口不同会导致行为漂移。

**决策：** `AGENTS.md` 提供 Codex 的简洁阅读顺序；`CLAUDE.md` 指向相同规则和完成定义。

**原因：** 减少重复维护，同时让两个工具遵循同一上下文和质量门槛。

**后果：** 稳定原则只维护在 `BOOK_RULES.md`、`STYLE_GUIDE.md` 和 `AI_BOOTSTRAP.md`。

**状态：** 已采纳。

## D004：Mermaid 优先

**背景：** 图示需要可审查、可版本控制并能与 Markdown 同步演进。

**决策：** 优先提交 Mermaid 源码；导出图仅为发布产物。

**原因：** 文本格式便于 diff、审查、复制和跨平台渲染。

**后果：** 每张图都需有源文件、读图说明和一致术语。

**状态：** 已采纳。

## D005：示例尽量可运行

**背景：** Harness 主题容易停留在抽象概念。

**决策：** 示例优先最小可运行闭环，明确环境、命令和成功条件。

**原因：** 可运行示例是书稿的测试用例，能暴露接口和叙述的不一致。

**后果：** 不可运行示例必须明确标注假设与限制；不得伪造执行结果。

**状态：** 已采纳。

## D006：章节采用 Research → Outline → Draft → Review → Validate

**背景：** 直接生成正文容易遗漏引用、示例和技术审查。

**决策：** 所有章节沿用固定的十阶段工作流，核心顺序为 Research → Outline → Draft → Review → Validate。

**原因：** 将知识收集、论证、实现和校验分离，使状态可见且可复用。

**后果：** `.ai/progress.md` 按阶段记录；阶段跳过必须说明理由。

**状态：** 已采纳。

## D007：项目状态持续更新

**背景：** 多 Agent 接力最常见的问题是任务和现实状态脱节。

**决策：** 每项完成任务必须更新 `CURRENT_STATE.md`、`NEXT_TASK.md` 和 `.ai/progress.md`。

**原因：** 让仓库而非对话成为后续工作的事实来源。

**后果：** 未同步状态的交付不满足 Definition of Done。

**状态：** 已采纳。

## D008：将 58 个主题收敛为 47 章

**背景：** 原始目录覆盖完整，但“模型/运行环境”“自改进/长期运行”“Claude Code/Codex”等主题存在共同前提，单列会迫使读者重复建立同一心智模型。

**决策：** 合并 11 组相邻主题为 47 章：模型、Agent 与运行环境；自改进与长期运行；Claude Code 与 Codex；Flutter 与需求到报告闭环；pytest 与 Playwright；模式、评估与审批等。

**原因：** 每章应围绕一个可完成的工程问题，而不是一个名词；合并后更利于案例、图示和依赖设计。

**后果：** 详细映射保存在 `.ai/outline.md`；附录仍完整保留 12 类可复用资产。

**状态：** 已采纳，P0 审查时可依据重叠证据调整。

## D009：P0 审查保留 47 章结构

**背景：** 初始化时已将 58 个主题收敛为 47 章；P0 需要验证剩余章节是否仍有重复，且确认读者不会在未建立前提时进入案例或模式章节。

**决策：** 保留 47 章，不新增合并。补充跨部分的最小阅读依赖和五组易混淆章节的责任边界。

**原因：** 目录中相邻章节共享术语，但分别回答系统定义、接口设计、领域案例、模式归纳或跨工具接力等不同问题。再合并会使一个章节同时承担多个案例和验收目标。

**后果：** 后续章节写作必须遵守 P0 依赖契约；如正文出现相邻章节重复，再以事实和读者任务为证据重开本决策，而不是继续扩写重复内容。

**状态：** 已采纳。

## D010：使用 GitHub Pages 与 GitHub Release 承载出版物

**背景：** 网站、PDF 与 EPUB 已能从同一内容清单本地生成，但缺少与仓库版本绑定的在线入口和离线归档。仓库远端位于 GitHub，现有站点是静态 VitePress，不需要新增运行时服务。

**决策：** `main` 更新后由 GitHub Actions 构建并部署 GitHub Pages；GitHub Release 发布后，从该 Release 的标签提交重新生成 PDF 与 EPUB，并上传到对应 Release。工作流不创建标签、Release 或书稿许可证。

**原因：** Pages 直接承载现有静态构建，Release 资产天然按标签隔离；两者都能复用 `publication/book-manifest.mjs`，避免网站与离线版本产生第二套内容顺序。

**后果：** VitePress 必须支持 Pages 子路径；Linux 发行构建需要显式安装中文字体并覆盖本地字体元数据。首次 Pages 启用、版本号、Release 创建和书稿许可证仍需维护者执行。

**状态：** 已采纳，2026-07-26。
