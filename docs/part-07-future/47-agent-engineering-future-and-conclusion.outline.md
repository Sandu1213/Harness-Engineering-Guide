# 第 47 章大纲：Agent Engineering 的未来与结语

## 本章要完成的学习目标

读者完成本章后，应能：

1. 区分随产品变化的实现与相对稳定的工程责任，不把当前能力写成未来保证；
2. 用任务、上下文、能力、状态、证据、评估与人类责任七个问题审查 Agent 系统；
3. 将模型变化、长时程状态、多 Agent、评估、安全、供应链和组织责任写成可调查的开放问题；
4. 以语法、契约、状态、证据和治理五层判断互操作，而不把连接成功当语义兼容；
5. 把一个一次性脚本沿最小、可验收的阶段升级为受限 Harness；
6. 为自己的下一项真实任务写出低风险实践路线和停止条件。

**前置章节：** 全书第 1 至 46 章；重点回收第 2、9、10、11、14、17、26、35、39、41、43 至 46 章。

**章节边界：** 本章不预测模型能力、厂商胜负、市场规模、标准采用、价格或时间线；不宣称全书工件已经出版；不设计万能 Agent 架构；不运行模型、工具、权限、安全测试、供应链或组织流程；不以 NIST、OWASP、SLSA 或产品指南推导法规、认证和固定控制。

## 叙事主线

以一个一次性自动化脚本为起点：它能调用模型或工具，却没有任务契约、状态、能力边界、效果证据、回归、交接或责任者。全章逐步加入最小必要责任，最终只到 `ready_for_bounded_pilot_review`，不直接进入生产。模型能力变化作为外部输入，不能跳过任何权限、证据或批准门。

## 逐节蓝图

### 1. 开场：未来最危险的不是变化，而是无版本的确定性

- **读者问题：** 为什么不能用当前 Demo 预测未来工程？
- **场景：** 模型快照、Tool Schema 或 Skill 变化后，一次性脚本仍输出结果，但没有人知道基线、权限和评估是否有效。
- **来源映射：** CH47-REF-01 仅支持 OpenAI 当前产品中的快照变化与 eval 建议。
- **核心结论：** 对未来保持开放，不等于没有工程原则；变化越快，版本、边界和证据越重要。
- **失败出口：** 无版本身份或评估时只写 `behavior_unverified`，不写“仍然兼容”。

### 2. 七项稳定责任：实现可以换，问题不能消失

- **任务契约：** 目标、非范围、输出、停止、验收和责任者。
- **上下文边界：** 来源、可见范围、版本、新鲜度与撤销。
- **能力边界：** Tool、目标、副作用、权限、预算和批准。
- **状态恢复：** 计划、运行、停止、重试、检查点、冲突和接力。
- **观察证据：** Tool Result、独立 Observation、验收与效果未知。
- **评估变更：** 任务集、基线、评分器、硬门和可比较性。
- **人类责任：** 风险所有者、例外、外部效果、申诉和停用。
- **验证：** 每项给出最小工件和保守失败状态；名称明确为本书模型。

### 3. 模型变化与长时程状态：不把容量当可靠性

- **模型开放问题：** 快照变化、可变输出、能力边界、旧评估失效和回归发现。
- **状态开放问题：** 长上下文、会话历史、长期记忆、检索和工作流状态的职责分离。
- **核心边界：** 更多 Token 或更强模型不证明来源、新鲜度、权限、恢复和删除正确。
- **来源映射：** CH47-REF-01、03 提供版本与持续评估背景；具体 Context/Handoff 责任来自第 6、7、13、19、45 章。
- **读者输出：** 为一个模型/上下文变化写失效矩阵，而不是能力预测。

### 4. 多 Agent 与评估效度：更多尝试不等于更多真相

- **多 Agent 开放问题：** 子任务独立性、共享写入、输入漂移、冲突合并、递归委派与协调成本。
- **评估开放问题：** 真实任务代表性、稀有失败、模型评分器偏差、隐私受限数据、长任务结果和组织目标冲突。
- **来源映射：** CH47-REF-03 只支持任务特定、边缘/对抗、持续评估与人工校准背景。
- **硬边界：** 投票、平均分和更多测试不能覆盖权限、安全、结果或发布硬门。
- **验证：** 要求读者为并行收益与协调成本分别定义观察证据。

### 5. 安全工具生态与 Agent 供应链

- **安全开放问题：** 不可信内容、间接 Prompt Injection、工具目标替换、记忆污染、数据泄露和效果未知。
- **供应链开放问题：** Prompt、Skill、Tool Schema、MCP Server、模型、依赖、评估集、策略的来源/版本/审查/分发/撤销。
- **来源映射：** CH47-REF-05 说明多种 Prompt Injection 风险；CH47-REF-06 仅提供软件供应链完整性的受限类比。
- **本书模型：** Agent Asset Register 与 Capability Grant Record 必须分开；资产可信不等于本次调用授权。
- **失败出口：** 来源、目标、版本或撤销状态不明时返回 `supply_chain_review_required` 或 `not_authorized`。

### 6. 组织责任：Human-in-the-loop 不是责任人姓名

- **读者问题：** 为什么模型、审查 Agent 或“人工参与”不能承担组织决定？
- **来源映射：** CH47-REF-04 支持风险管理跨 GOVERN、MAP、MEASURE、MANAGE 与生命周期背景。
- **本书模型：** Human Responsibility Map 记录风险所有者、受影响者、独立审查者、批准/停止/申诉/事件责任。
- **反例：** `human_approved: true` 没有主体、范围、输入版本、理由和有效期。
- **边界：** 责任映射不证明法律义务、伦理充分或组织治理有效。

### 7. 标准化五层阶梯：连接、兼容、可验证、可治理不是同一层

- **语法层：** 字段能解析，版本可识别。
- **契约层：** 输入、输出、错误、副作用、幂等和目标语义明确。
- **状态层：** 计划、执行、观察、验证、停止不互相冒充。
- **证据层：** 来源、运行、版本、未覆盖和责任可追溯。
- **治理层：** 权限、隐私、审计、例外、撤销和人类决定可执行。
- **案例：** 两个工具都返回 `success`，一个表示请求接受、另一个表示业务效果完成，语法兼容但状态语义冲突。
- **结论：** 标准价值由失败语义与责任边界判断，不由字段数量或生态宣传判断。

### 8. 演进案例：一次性脚本到受限 Harness

- **Stage 0：** 固定输入/输出与可重复样例。
- **Stage 1：** Task Contract 与失败出口。
- **Stage 2：** 状态机、原因码与 Attempt Trace。
- **Stage 3：** Tool/Capability Contract、目标和副作用边界。
- **Stage 4：** Result、Observation、验收和 `effect_unknown`。
- **Stage 5：** Evaluation Spec、版本基线、拒绝/故障场景和硬门。
- **Stage 6：** Context/Handoff Package、Checkpoint 和冲突记录。
- **Stage 7：** 只有收益可测、权限/预算/停止/回滚有效时增加受限自治。
- **来源映射：** CH47-REF-02 只支持从简单方案开始；阶段与工件均为本书综合。
- **终点：** `ready_for_bounded_pilot_review`，不是生产上线。

### 9. 读者实践路线：从一个低风险任务开始

- 选择可检查输入、可回滚输出和具名责任者的只读或候选生成任务。
- 先写缺输入、缺权限、工具失败、效果未知、不可比较和需批准的失败出口。
- 保存一条完整但最小化、去敏的 Attempt Trace。
- 建立正常、拒绝、边界和故障组成的最小回归集。
- 让另一位人或工具在不读原聊天的情况下从仓库工件接手。
- 只为实际失败与可测收益增加并行、记忆、路由或自治。
- **验证：** 每步都有“完成证据”和“仍不能声称”的列。

### 10. 计划纯内存示例：`assessAgentEngineeringReadiness(input)`

- **输入：** `taskContract`、`contextBoundary`、`capabilityBoundary`、`stateModel`、`observationEvidence`、`evaluationEvidence`、`handoffEvidence`、`riskOwnership`、`autonomyRequest`。
- **输出：** `needs_contract`、`needs_capability_boundary`、`needs_effect_evidence`、`evaluation_not_comparable`、`handoff_not_ready`、`human_accountability_required` 或 `ready_for_bounded_pilot_review`。
- **TDD 路径：** 缺契约、上下文过期、能力越权、状态混淆、只有 Tool Result、评估版本不一致、交接漂移、无风险所有者、过早自治和完整受限候选。
- **副作用边界：** 不调用模型/Tool，不读取系统，不修改权限，不部署、发布或启动 Agent；固定 `executionPerformed: false`。

### 11. 计划图示：模型变化下的 Harness 演进地图

- **图源：** `diagrams/mermaid/chapter-47-agent-engineering-evolution-map.mmd`。
- **主轴：** 一次性脚本 → 契约 → 状态 → 能力 → 观察 → 评估 → 交接 → 受限自治。
- **跨层约束：** 模型能力变化、组织风险、标准、安全和长期学习系统。
- **硬断点：** 模型能力提升不自动扩大权限；协议连接不等于语义互操作；Eval 通过不等于上线批准；自治增加后仍能停止/回滚/交给人类。
- **验证：** Mermaid CLI 11.16.0 导出 SVG/PNG，正文块与 `.mmd` 逐字一致并视觉检查。

### 12. 结语：工程成熟度是更诚实地知道系统能证明什么

- 回收从 Prompt 到 Harness 的主线：Prompt 是输入，Harness 承担上下文、能力、状态、证据和责任。
- 回收全书“计划、执行、观察、验证、完成”不能互相替代。
- 强调未来不是由自治程度衡量，而是由外部效果可控、失败可见、证据可追溯、责任可承担衡量。
- 将未知保留为开放问题和下一次评估输入，不用结语制造确定性。
- 最终通知边界：只有全 47 章阶段、共享状态和全仓验证新鲜通过，才可将本书工程工件标记完成；完成不等于出版。
