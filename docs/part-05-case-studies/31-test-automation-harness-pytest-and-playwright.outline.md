# 第 31 章详细 Outline：测试自动化 Harness：pytest 与 Playwright

## 写作契约

### 本章要完成的学习目标

读者完成本章后应能：

1. 为同一登录场景分别声明 API Contract Check 与 UI Flow Evidence，并说明任一层的通过不能替代另一层。
2. 使用 pytest fixture 与 `monkeypatch` 的受限语义设计准备、替身和恢复边界，而不把替身写成真实依赖。
3. 说明 Playwright Browser Context、locator 和可重试断言各自提供的有限测试机制，以及仍需保留的用户动作前后证据。
4. 用 Failure Record 和 Report Gate 区分 API、隔离、定位、观察和业务失败，避免用“flaky”掩盖缺口。
5. 在真实服务或浏览器尚未运行时，写出诚实的 Test Evidence Plan 与升级条件。

### 读者、前置与明确边界

- **读者：** 能读基础 Python、JavaScript 对象和测试表格，且需要把接口测试与浏览器流程测试组织为可审查工作的工程读者。
- **前置：** 第 17 章的评估与可验证结果、第 25 章的浏览器交互证据、第 28 章的最小 Harness、第 29 章的软件交付包和第 30 章的应用交付证据边界。
- **本章负责：** 用虚构登录场景组织 API 契约、UI 流程、隔离、观察、失败分类和报告门的关系。
- **本章不负责：** 真实 pytest／Playwright 项目初始化、依赖安装、HTTP 服务、浏览器会话、账户、凭证、网络模拟、CI、测试云、截图、性能、安全、发布或真实测试报告。

## 章节叙事与逐节蓝图

### 1. 为什么 API 200 不是用户成功

- **要回答的问题：** 一条接口成功响应为何不能替代用户可见登录流程？
- **场景输入：** 虚构登录 API 可返回成功、认证拒绝或服务错误；网页端还需要输入、点击提交并重新观察用户可见状态。
- **核心论证：** API Contract Check 和 UI Flow Evidence 共享场景标识，却具有不同目标、观察和失败面；把任一层的绿色结果升级为另一层结论会制造证据缺口。
- **最小证据：** 比较“响应状态／形状”和“动作前快照、主动作、动作后快照”分别能说明什么。
- **预期验证：** 读者能拒绝“200 所以登录成功”与“按钮可点击所以接口正确”两种结论。
- **过渡：** 先把两层证据及其限制写成统一计划，再讨论各自的隔离机制。

### 2. 测试证据计划：共享场景，不共享结论

- **要回答的问题：** 同一测试场景怎样分别约束 API 与 UI，而不让报告混为一行？
- **本书模型：** Test Evidence Plan 包含 `scenarioId`、API 契约、UI 观察链、隔离边界、Failure Record 要求和 Report Gate；这是教学合同，不是 pytest 或 Playwright 配置文件。
- **分层表：** API Contract Check 描述请求前提、响应形状、错误分类与替身；UI Flow Evidence 描述目标页面、动作前观察、点击／提交、动作后重新观察和有限断言。
- **最小证据：** 一个场景必须同时声明其 API 和 UI 证据，或明确说明缺失层与不能主张的结论。
- **预期验证：** 读者能指出缺少 UI 后观察时，API 结果不能填补该字段。
- **过渡：** API 层必须先控制依赖和恢复，再谈响应是否满足教学契约。

### 3. API 契约检查：fixture、替身与恢复边界

- **要回答的问题：** API 检查如何避免依赖上一次测试、开发者机器或真实服务？
- **来源事实：** REF-095 限定 pytest fixture 的请求、作用域及生命周期；REF-096 限定 `monkeypatch` 修改在请求方结束后撤销。
- **本书 API Contract Check：** 明确前提、受控输入、预期响应字段、认证拒绝／服务错误分类、fixture 作用域、替身目标和恢复条件。
- **最小证据：** 一张“fixture／替身 → 测试对象 → 预期响应 → 恢复检查”的计划表；不展示真实 URL、token、数据库或 HTTP 输出。
- **失败分类：** 缺前提、替身未恢复、响应形状不符、错误分类不符与未知真实依赖分别进入 Failure Record。
- **预期验证：** 读者能解释替身通过为什么不等于真实服务兼容。
- **过渡：** API 层控制了输入和依赖，但无法观察用户界面的交互结果。

### 4. UI 流程证据：Browser Context 只隔离浏览器状态

- **要回答的问题：** Browser Context 能消除什么状态泄漏，又不能消除什么？
- **来源事实：** REF-097 限定 Playwright 的每测试 Browser Context、独立 storage/cookies 与 clean-slate 语境。
- **本书 UI Flow Evidence：** 声明页面目标、上下文边界、动作前观察、主动作、动作后重新观察、期望可见状态和未覆盖的后端／账户风险。
- **最小证据：** 表格区分“Context 新建”与“用户流程被验证”；前者只处理浏览器状态，后者仍需一次具名主动作及前后观察。
- **失败分类：** 上下文状态泄漏、未授权环境、目标不可达、观察缺失和用户状态不符不能统称 UI 失败。
- **预期验证：** 读者能拒绝把独立 cookies 或新的页面实例写成用户登录成功。
- **过渡：** 界面已隔离后，下一步仍要用可审查定位和重新观察把动作连接到目标。

### 5. 定位、动作与可重试断言：观察必须晚于动作

- **要回答的问题：** 怎样避免脆弱 selector、静态等待和动作前旧快照？
- **来源事实：** REF-083 限定用户可见属性／显式测试契约定位和动作时当前 DOM 的解析；REF-082 限定 Web-first 异步断言重试至满足或超时。
- **本书定位选择门：** 优先可读的用户可见属性；只有存在明确维护约定时才用测试标识；CSS/XPath、任意 sleep 或未标识观察只能作为待诊断输入。
- **本书观察链：** `beforeObservation → primaryAction → afterObservation → limitedVerdict`；可重试断言减少异步读取竞态，但不替代主动作或业务验收。
- **最小证据：** 一张定位选择与观察新鲜度表，明确 afterObservation 必须晚于主动作且关联同一场景。
- **预期验证：** 读者能指出 locator 找到元素、断言超时或断言通过分别仍缺少什么证据。
- **过渡：** 两层测试可能各自失败，需要报告保存差异而非压缩成“测试挂了”。

### 6. Failure Record 与 Report Gate：让失败可路由，让结论可收缩

- **要回答的问题：** 如何使失败信息能指导下一步，而不是被“flaky”标签掩盖？
- **本书模型：** Failure Record 关联 `scenarioId`、layer、isolation、locator／substitute、observation、分类、限制和下一步；Report Gate 拒绝缺少关联、观察或限制的通过结论。
- **失败表：** API 契约差异、替身恢复问题、Browser Context 泄漏、定位失败、断言超时、动作后状态不符与环境未批准分开记录。
- **最小证据：** 原因码与补充动作表，不生成真实日志、截图、trace 或服务诊断。
- **预期验证：** 读者能为“API 通过而 UI 后观察缺失”选择缺失证据，而非判定整体通过。
- **过渡：** 下一节将计划收束为无副作用的准入器，防止测试计划悄悄启动环境。

### 7. 最小示例：纯内存测试证据计划准入器

- **要回答的问题：** 怎样让两层测试的证据边界可运行、可反驳，又不启动真实测试？
- **示例边界：** 后续 `assessTestEvidencePlan(plan)` 只检查注入对象；不得执行 pytest、Playwright、HTTP、浏览器、文件、子进程、账户、凭证、网络或 CI。
- **计划返回：** 完整教学计划可返回 `ready` 与“在隔离示例中实现”的下一步；缺 API／UI 证据、隔离、动作后观察、失败分类或报告限制时返回 `stopped`；任何真实环境请求返回 `requires_approval`。
- **计划测试：** 完整双层计划、缺 API 合同、缺 UI 后观察、错误层关联、替身／Context 边界不足、报告声称执行及环境请求未批准。
- **预期验证：** Example Implementation 阶段先记录红灯，再以实际 Node 测试和演示确认纯函数；Outline 不将其写成当前结果。
- **过渡：** 图示需要把 API 与 UI 平行流和报告门画成不可跳过的断点。

### 8. 图示：两层测试如何汇入有限报告

- **要回答的问题：** 一张图怎样同时表达 API 与 UI 的互补性和停止边界？
- **图示内容：** Test Evidence Plan 分别进入 API Contract Check 与 UI Flow Evidence；前者经过 fixture／替身边界，后者经过 Browser Context、locator、动作和重新观察；二者各自写入 Failure Record 或 Observation Record，Report Gate 只接受关联完整的有限结论。
- **关键箭头解释：** 无“API 200 → 用户成功”、无“Browser Context → 业务通过”、无“locator → 报告通过”的箭头；环境请求先指向批准出口。
- **工件与验收：** 正文 Mermaid 块与未来图源逐字一致；SVG／PNG、替代描述和可读性在 Diagram Review 阶段核验。
- **过渡：** 图保留证据断点，下一节以同一登录场景说明如何同时填两条路径。

### 9. 完整教学案例：同一登录场景的 API 与 UI 证据

- **要回答的问题：** 同一场景怎样让 API 错误分类和 UI 可见状态相互补充？
- **案例组织：** 以成功登录、认证拒绝和服务错误为行，以 API 契约、UI 主动作、动作后观察、Failure Record 和当前报告限制为列。
- **关键决策：**
  1. API 成功响应只能作为 API 层观察，不能替代页面提交后的状态观察。
  2. UI 流程必须使用具名场景、前后观察与当前 locator；不可用旧快照或页面加载替代提交动作。
  3. fixture／替身和 Browser Context 只收缩依赖／浏览器状态，不授予服务、账户或数据真实性。
  4. 报告必须保留层级和限制；缺一层时只报告已观察层，而非“登录已通过”。
- **最小证据：** 只使用虚构场景标识，不展示 URL、cookie、账号、token、请求包、服务日志或截图。
- **预期验证：** 读者能为一条 API 已观察、UI 未运行的场景写出诚实报告。
- **过渡：** 若要进入真实项目，需要按风险逐项增加环境控制与实际观察。

### 10. 逐步增强、总结与后续连接

- **要回答的问题：** 从纯内存计划到真实测试 Harness，每一步为什么必须增加控制？
- **渐进表：**

| 新需求 | 必须新增的控制 | 升级触发 | 本章为何不实现 |
| --- | --- | --- | --- |
| 运行 pytest API 测试 | 受控服务、命令、依赖锁定、输出和清理。 | 要观察真实接口行为。 | 本章 Research／Outline 不创建服务。 |
| 运行 Playwright UI 流程 | 获批浏览器目标、Context、前后观察、失败工件和清理。 | 要主张用户可见流程。 | 本章不启动浏览器或账户。 |
| 使用真实认证或数据 | 最小权限、凭证处理、数据策略和后端契约。 | 要触及真实身份或网络。 | 教学输入禁止此动作。 |
| 发布测试报告 | 关联 Observation Record、Failure Record、限制和人工审核。 | 要向团队作执行结论。 | Report Gate 不产生事实。 |
| 诊断失败并修复 | 最小复现、可证伪假设、回归测试与复盘。 | 已有真实失败观察。 | 留给第 32 章。 |

- **总结回收：** 测试 Harness 的价值不在于堆叠框架，而在于让 API、UI、隔离、观察、失败与报告各自只声明其证据能支持的结论。
- **练习：** 要求读者补一条 API 契约、一条 UI 后观察、一个隔离边界和一个报告限制；再指出 API 通过但 UI 未运行时能够主张的唯一结论。
- **后续连接：** 第 32 章在真实失败观察已经存在时处理最小复现、假设和回归；第 39 章再扩展到 Harness 的测试策略与 Benchmark。
