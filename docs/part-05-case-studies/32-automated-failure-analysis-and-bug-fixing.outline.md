# 第 32 章详细 Outline：自动分析失败并修复 Bug

## 写作契约

### 本章要完成的学习目标

读者完成本章后应能：

1. 区分症状、复现条件、候选原因和已验证修复，不把错误文本或一次绿色检查写成根因结论。
2. 为一个失败建立 Reproduction Contract，并说明最小样例必须仍满足同一个失败判定。
3. 用 Hypothesis Record 写出可证伪预测、低风险检查、观察与支持／推翻／未决状态，而非只列“可能原因”。
4. 把候选修复与 Regression Gate 分开，要求原失败路径、修复后预期行为与未覆盖范围同时可审查。
5. 在复现不稳定、证据不足、风险升高或达到项目约束时留下 Escalation Record，而非继续猜测或自动修改共享环境。

### 读者、前置与明确边界

- **读者：** 能读基本测试、日志／状态表和 JavaScript 对象，且需要把失败调查转化为可审查工程流程的读者。
- **前置：** 第 15 章的 Observation Record、第 16 章的 Reflection Record 与 Falsifiable Check、第 17 章的评估规格、第 18 章的恢复边界、第 29 章的软件变更交付包与第 31 章的 API／UI 测试证据。
- **本章负责：** 用虚构的偶发 UI 等待条件失败说明症状收集、受控复现、最小化、模式搜索、可证伪假设、候选修复、回归门、升级和复盘的关系。
- **本章不负责：** 自动根因分析、真实 Bug 修复、真实 pytest／Playwright、浏览器、HTTP、Git bisect、文件、子进程、CI、生产日志、账户、凭证、发布、事故处置或环境变更。

## 章节叙事与逐节蓝图

### 1. 从症状开始：错误文本不是根因

- **要回答的问题：** 为什么“测试超时”或“某元素不存在”只能说明观察到的症状？
- **场景输入：** 虚构网页登录检查在提交后偶发未观察到目标状态；已知信息只有场景标识、预期可见结果、实际缺失观察和一次受限失败记录。
- **来源事实：** REF-099 的问题报告语境要求尽量给出预期行为、实际行为和复现方式；它不把单个报告等同根因。
- **本书 Bug Investigation：** 记录范围、症状、预期、实际、关联、可用观察、未知变量、风险与停止条件；其第一条规则是“症状不是根因”。
- **最小证据：** 对照表将“动作后没有观察”与“等待条件错误”分列，后者必须标为候选假设。
- **预期验证：** 读者能拒绝把异常消息、日志关键词或单个超时直接改写为修复任务。
- **过渡：** 有了明确症状，先让失败判定与条件可复查，才能谈调查效率。

### 2. Reproduction Contract：先定义“同一个失败”

- **要回答的问题：** 最小复现如何避免把“问题消失”误当成“问题被定位”？
- **来源事实：** REF-098 的 `ddmin` 讨论通过连续测试把失败样例缩小到仍然触发失败的最小样例。
- **本书 Reproduction Contract：** 声明 `symptomId`、受控输入、前置状态、失败判定、允许动作、被观察变量、不可信变量和禁止触及的环境；它是教学合同，不是测试运行器配置。
- **最小证据：** 示例表明确每次缩小后必须用同一失败判定检查；不展示真实 URL、账号、提交、日志或命令输出。
- **失败分支：** 缩小后失败消失、条件不完整、环境未获批或观察无法关联时，只能标记 `not_reproducible`／`insufficient_evidence`／`requires_approval`，不能宣称已修复。
- **预期验证：** 读者能说明“更短的测试”只有仍触发同一症状时才有调查价值。
- **过渡：** 稳定失败条件出现后，才能用最少变量搜索是否存在一个更小的失败诱因。

### 3. 最小化与差异：缩小输入，不缩小证据标准

- **要回答的问题：** 何时用减法最小化，何时比较通过／失败差异？
- **来源事实：** REF-098 区分失败样例最小化与通过／失败样例差异隔离；论文本身不承诺每类系统均可自动完成。
- **本书最小化表：** 将候选变量分成输入片段、状态前提、顺序、等待条件和外部未知项；每次只移除或改变一类变量，并保留失败判定与关联标识。
- **最小证据：** 一组虚构“失败／通过”条件只能用于说明差异表，不能用来声称真实 UI、浏览器或服务已经复现。
- **停止条件：** 连续观察不一致、变量无法隔离、可能影响共享环境或继续缩小会改变失败判定时，停止最小化并转向记录未知项。
- **预期验证：** 读者能解释“最小”是相对于所声明失败判定的，不是“代码行数最少”或“因果已证明”。
- **过渡：** 若失败与通过条件包含变化区间，下一节说明如何只在具备边界和许可时用二分缩小调查范围。

### 4. 模式搜索与变化区间：二分只缩小嫌疑集合

- **要回答的问题：** 历史变化、相似失败和组件边界如何帮助排序调查，而不制造虚假的因果链？
- **来源事实：** REF-100 限定 Git `bisect` 以至少一个 good 与一个 bad 提交为边界、测试中点并最终报告第一个 bad 提交的 Git 行为。
- **本书模式搜索：** 在已获准且具备通过／失败边界时，比较症状记录、近期受控变更、相似 Failure Record 和组件数据流；二分输出只是“待检查变化”，不是根因。
- **最小证据：** `knownGood`、`knownBad`、可重复的性质检查、候选范围和工作树／环境边界；任一缺失则不应开始二分。
- **失败分支：** 历史不可用、提交无法构建、症状不稳定、检查改变环境或操作未获批时，写入 Escalation Record，不改写 Git 状态。
- **预期验证：** 读者能说明第一个 bad 提交可帮助定位引入变化，但还必须解释机制并用独立检查排除替代原因。
- **过渡：** 嫌疑集合缩小后，Agent 需要形成可被反驳的具体假设，而不是无限罗列可能性。

### 5. Hypothesis Record：让每个原因候选都能被推翻

- **要回答的问题：** 怎样把“可能是等待问题”改写成可操作的工程假设？
- **来源事实：** REF-099 把排障描述为根据观察与系统理论迭代提出并测试候选原因；检查可以寻找支持或反证，理想检查可排除一组替代假设。
- **本书 Hypothesis Record：** 每项包含 `hypothesisId`、机制、现有观察、预测、反事实、最低风险检查、预期读数、风险、结果与状态；没有预测和检查的条目必须标为 `unshaped`，不能进入修复。
- **排序规则：** 按证据相关性、可区分性、检查风险和成本排序；不使用跨项目固定权重或失败次数。
- **最小证据：** 为“动作后观察早于可观察状态”写出：若成立，受控等待条件检查应与观察缺失相关；若不成立，应检查目标、状态或服务层证据。
- **预期验证：** 读者能给出一个会失败的预测，而非只列出一个看似合理的解释。
- **过渡：** 假设写清后，下一节选择最低风险的可证伪检查，并记录负面结果。

### 6. Falsifiable Check：检查要区分假设，不能只制造更多噪声

- **要回答的问题：** 为什么同一条日志、同一段 sleep 或一次重跑通常不是足够的诊断检查？
- **来源事实：** REF-099 提醒主动检查可能有副作用或受混杂因素影响，并建议清楚记录想法、所做检查和结果。REF-081 的 actionability／自动重试只适用于 Playwright 的指定动作和断言语境。
- **本书检查设计：** 固定关联、先观察后比较、一次只改变一个变量、预先写出支持与推翻的读数；若检查有副作用，必须先声明恢复或升级条件。
- **虚构案例：** 只在纯教学对象中比较“提交动作后立即读取”与“关联到目标可观察条件的重新观察”；不创建 Playwright 测试，不等待真实页面。
- **最小证据：** Hypothesis Record 的检查字段和 Observation Record 的新鲜度字段能关联同一 `symptomId`。
- **失败分支：** 读数模糊、检查改变被测状态、需要真实环境或无法辨别两个候选原因时，保持 `unresolved` 并升级。
- **预期验证：** 读者能说明某条检查推翻了什么、仍未覆盖什么，而不是只报告“又试了一次”。
- **过渡：** 只有某一假设获得受限支持后，才有资格提出最小候选修复。

### 7. Fix Candidate：候选补丁只服务于已关联假设

- **要回答的问题：** 怎样避免把调查中顺手想到的重构、延时或重试直接变成修复？
- **本书 Fix Candidate：** 关联一个 `hypothesisId`、声明最小改变、预期影响、拒绝触及的范围、回滚／恢复假设和待验收的回归条件；它不是文件写入、Git 操作、合并批准或发布许可。
- **最小证据：** 只有被支持但仍有边界的假设能产生候选补丁；未决或已推翻假设只能保留记录，不能触发变更。
- **常见误区：** 增加任意 sleep、扩大 timeout、吞掉异常、跳过失败测试或混入无关重构都会损害失败判定，不构成修复。
- **预期验证：** 读者能把“将观察改为动作后、关联具体可观察条件”写成候选，而不把它描述为已经修改并通过。
- **过渡：** 候选变化必须重新面对原症状和预期行为，下一节定义回归门。

### 8. Regression Gate 与升级：绿色结果仍需限定结论

- **要回答的问题：** 怎样在不把一次通过夸大为交付成功的前提下，判断候选修复是否可接受？
- **来源事实：** REF-099 讨论通过反复测试定位原因、采取纠正动作和保留复盘；该书不提供本章的回归 schema、次数或发布规则。
- **本书 Regression Gate：** 同时要求原症状的 Reproduction Contract、候选变化后的预期观察、相关范围检查、失败／未知结果、未覆盖项和报告限制。缺任一项只能返回 `not_ready` 或 `requires_escalation`。
- **Escalation Record：** 复现不稳定、假设均被推翻、检查风险升高、需要共享环境／真实凭证、或达到项目定义的尝试约束时，记录证据、已排除项、未决问题与人工所需决定。
- **最小证据：** 回归门表明确“原失败不再出现”与“预期行为被观察”是两项独立条件；两者都不等同发布验收。
- **预期验证：** 读者能拒绝“测试绿了，所以发布”并指出应保留的范围与审批。
- **过渡：** 调查的负面结果和证据边界应留下可复用但可撤销的经验，而不是混入规则或记忆。

### 9. 最小示例：纯内存缺陷调查准入器

- **要回答的问题：** 如何把调查闭环变成可测试契约，而不复现真实 Bug 或修改代码？
- **示例边界：** 后续 `assessBugInvestigation(investigation)` 只检查注入对象；不得执行 Bug 修复、pytest、Playwright、Git、浏览器、HTTP、文件、子进程、网络、账户、凭证、CI 或环境动作。
- **计划返回：** 完整教学调查可返回 `ready` 与“在隔离示例中实现”；缺复现判定、未塑形假设、无区分性检查、候选修复未关联假设、回归门缺原失败／预期行为或环境请求未批准时返回 `stopped`／`requires_approval`。
- **计划测试：** 完整调查、缺症状边界、不可复现、缺预测、检查不能区分、已推翻假设仍请求修复、缺回归分支、报告声称执行及环境请求。
- **预期验证：** Example Implementation 阶段先记录模块缺失红灯，再以实际 Node 测试和演示证明纯函数；Outline 不将计划写成当前结果。
- **过渡：** 图示需要让症状、调查、候选、回归和升级之间的断点一眼可见。

### 10. 图示、完整教学案例与逐步增强

- **要回答的问题：** 如何让读者同时看见调查顺序、可反驳性与不能自动越过的边界？
- **图示内容：** `Symptom Record → Bug Investigation → Reproduction Contract → Minimize / Compare → Hypothesis Record → Falsifiable Check → Fix Candidate → Regression Gate`；未决、风险过高或证据不足的分支进入 Escalation Record，再进入 Reflection Record。
- **关键箭头解释：** 无“症状 → 根因”、无“候选修复 → 完成”、无“回归绿色 → 发布”的箭头；真实环境请求先指向批准出口。
- **教学案例矩阵：** 以虚构的“动作后观察缺失”为行，以症状、最小化条件、候选假设、区分检查、候选修复、回归门和当前限制为列；不得展示真实 trace、截图、账户、URL、提交或命令输出。
- **渐进表：**

| 新需求 | 必须新增的控制 | 升级触发 | 本章为何不实现 |
| --- | --- | --- | --- |
| 复现真实 UI 失败 | 获批目标、隔离、前后观察、数据与清理策略。 | 要主张浏览器行为。 | 本章不启动浏览器。 |
| 对历史执行 Git bisect | 通过／失败边界、可重复性质、工作树和变更批准。 | 要缩小真实引入区间。 | 本章不操作 Git 状态。 |
| 写入候选修复 | 明确路径、最小权限、测试、审查、回滚和批准。 | 候选已过回归门且需要落盘。 | 本章不修改真实项目代码。 |
| 发布修复结论 | 真实观察、影响范围、未覆盖项、人工审核和发布流程。 | 要影响用户或共享环境。 | Regression Gate 不产生发布事实。 |

- **总结回收：** 自动分析失败不是自动猜修复；可靠的 Harness 让每个症状、复现、假设、检查、候选、回归和升级只承担其证据能够支持的结论。
- **练习：** 要求读者为一个偶发失败写 Reproduction Contract、两条互相可区分的 Hypothesis Record、一个拒绝任意 sleep 的 Fix Candidate 和一条带未覆盖范围的 Regression Gate。
- **后续连接：** 第 33 章把调查中的稳定、可验证经验纳入项目记忆；第 39 章再讨论 Harness 的测试策略与 Benchmark，不能倒过来以指标替代根因调查。
