# 第 33 章详细 Outline：Obsidian 项目记忆系统

## 写作契约

### 本章要完成的学习目标

读者完成本章后应能：

1. 区分文件夹、属性、链接和标签的不同职责，不把任一机制当成项目记忆的完整模型。
2. 为一条记忆节点（Memory Node）声明稳定标识、用途、生命周期、责任、复核时间和后继动作，并说明字段存在不证明内容正确。
3. 用链接契约（Link Contract）区分“来源支持”“审查覆盖”“阻塞”“替代”和“下一步”等关系，避免把可点击链接误当成已核验结论。
4. 用记忆健康检查（Memory Health Check）将缺来源、缺状态、失效关系和过期复核路由为补证或人工复核，而不是自动修改笔记。
5. 在跨设备或多人协作前，以同步边界（Synchronization Boundary）记录范围、负责人、冲突出口和备份责任，不把同步功能视为写入授权或一致性保证。

### 读者、前置与明确边界

- **读者：** 能阅读 Markdown、YAML front matter 和相对链接，且需要让人类与 Agent 在长期项目中恢复上下文的工程读者。
- **前置：** 第 03 章的仓库上下文、第 07 章的工作／长期记忆、第 13 章的来源与检索、第 16 章的经验准入、第 19 章的压缩与恢复，以及第 31、32 章的测试与失败证据边界。
- **本章负责：** 用受限的 Obsidian 文件、属性、链接、标签和同步资料作为背景，提出项目记忆层的节点、关系、生命周期、健康检查和同步边界模型。
- **本章不负责：** 创建或打开 vault、读取或修改本地笔记、安装插件、调用 Obsidian、Obsidian Sync、Git、云盘、网络、Agent 工具、账户、设备、订阅、备份、冲突解决、权限配置或真实项目迁移。

## 章节叙事与逐节蓝图

### 1. 从笔记堆到项目记忆：可保存不等于可接力

- **要回答的问题：** 为什么文件没有丢失，下一位读者仍可能无法找回一条结论的来源、当前状态和下一步？
- **场景输入：** 使用虚构的“第 31 章登录测试证据”记忆网：章节节点、研究简报、来源卡、测试证据计划、图示审查、事实核验和未决问题分散在不同位置。
- **核心论证：** 项目记忆层（Project Memory Layer）服务于定位、追溯、交接和复核；它不等同于聊天摘要、目录树、Obsidian Graph view 或一个无边界的知识库。
- **最小证据：** 用两列比较“只有文件名与文件夹”能回答的问题，和“节点、关系、状态、责任与后继动作”额外回答的问题。
- **预期验证：** 读者能指出一条“测试已完成”笔记若缺来源、复核时间和限制，不能成为可复用项目结论。
- **过渡：** 若要让记忆可定位，先必须把物理归属与语义关系拆开。

### 2. Vault 与目录归属：文件路径只回答主要归属

- **要回答的问题：** Vault 和文件夹能提供什么结构，又为什么不能替代状态与关系？
- **来源事实：** REF-101 仅用于说明 Obsidian vault 中 Markdown 纯文本笔记、本地文件夹和外部变化刷新的产品背景。
- **本书目录规则：** 在项目记忆层中，目录用于声明主要归属，例如 `chapters/`、`sources/`、`reviews/`、`decisions/` 与 `archive/`；路径不是唯一身份、事实判断、访问许可或同步状态。
- **最小证据：** 为虚构 `chapter-31`、`source-ref-097` 和 `review-ch31-fact-check` 指定主要归属，并单列它们仍缺少的关系和生命周期信息。
- **失败分支：** 路径重组、同一事实被复制、文件在目录外、读取权限未知或外部变更来源未知时，保留不确定性并转入人工复核；不假设应用刷新等于内容无冲突。
- **预期验证：** 读者能解释“放入正确文件夹”不证明笔记已被读到、仍然新鲜或可以作为下一步依据。
- **过渡：** 目录给出归属后，节点需要结构化字段描述其当前可用性。

### 3. Memory Node 与 Lifecycle Record：字段描述状态，不替代判断

- **要回答的问题：** 一个可交接记忆节点最少需要说明什么，才能让读者知道它处于何种生命周期？
- **来源事实：** REF-102 仅用于说明 Obsidian Properties 的顶部 YAML 结构化字段和同名属性类型语境。
- **本书 Memory Node：** 每个节点至少声明 `id`、`kind`、`status`、`owner`、`reviewed_at` 与 `next_action`；这些是本书教学字段，不是 Obsidian 强制 schema。
- **本书 Lifecycle Record：** 以 `collected`、`under_review`、`stable`、`superseded`、`archived` 与 `pending_removal` 说明工作状态，并附替代指针或后继动作。字段值不自动移动、删除、通知或批准任何内容。
- **最小证据：** 将虚构的来源卡标为 `under_review`、测试证据计划标为 `stable`、过时审查结论标为 `superseded`，并说明每一种状态不能主张的事实。
- **失败分支：** 缺稳定标识、状态不在允许集合、`stable` 节点缺复核时间、`superseded` 节点无替代目标或没有下一步时，健康检查只能返回补证／复核需求。
- **预期验证：** 读者能区分“YAML 中有 `status: stable`”和“该结论已通过独立事实审查”。
- **过渡：** 节点自身不足以表达证据链，下一节为连接节点的边规定含义。

### 4. Link Contract：链接可追溯，不自动成立

- **要回答的问题：** 怎样让链接表达可审查关系，而不让一张密集知识网掩盖关系含义？
- **来源事实：** REF-103 仅用于说明 Obsidian 支持 Wikilink 与 Markdown 内部链接，以及重命名时可更新 vault 内链接的限定行为。
- **本书 Link Contract：** 每条核心关系声明 `from`、`relation`、`to`、方向和最小可检查条件；允许的教学关系包括 `supports`、`covers`、`blocks`、`supersedes` 与 `next_step`。
- **可移植性选择：** 跨工具关键关系优先约定 Markdown 相对链接；若展示 Wikilink，必须标记其 Obsidian 特定性。两者都不能证明外部渲染器、附件、块引用、Git 历史或人工语义关系会被保留。
- **最小证据：** 在虚构网中写出 `source-ref-097 supports chapter-31`、`review-ch31-fact-check covers chapter-31` 与 `chapter-31 next_step chapter-32`，并为每条关系写出被反驳时如何处理。
- **失败分支：** 目标缺失、关系类型不明确、链接格式与项目规则不符、替代链形成循环或跨工具兼容性未知时，保留 `needs_review`，不自动重写或删除链接。
- **预期验证：** 读者能识别“链接存在”与“来源支持该结论”之间仍需要的来源范围和人工判断。
- **过渡：** 有了具名关系后，标签只承担粗粒度发现，不承担图结构责任。

### 5. Tags 与检索：辅助发现，不承担身份、权限或依赖

- **要回答的问题：** 标签应如何帮助查找，而不替代目录、节点标识和链接契约？
- **来源事实：** REF-104 仅用于说明标签有助于查找、YAML `tags` 的列表形式与嵌套标签筛选的产品背景。
- **本书标签规则：** 标签只记录主题或粗粒度生命周期辅助，例如 `memory`、`chapter-31`、`needs-review`；稳定身份由 `id` 承担，主要归属由路径承载，关系由 Link Contract 承担。
- **最小证据：** 对同一个 Memory Node 比较 `id`、路径、`tags` 和关系边各自能回答什么；展示一个标签缺失时仍可由稳定链接定位的情形。
- **失败分支：** 标签层级被当作目录、同名标签含义漂移、敏感状态通过标签泄露、标签筛选遗漏关键节点或需要决定执行权限时，停止把结果升级为完整清单或授权判断。
- **预期验证：** 读者能说明“找到了 `#needs-review`”只能生成候选集合，不能证明所有待审内容均已列出。
- **过渡：** 节点、关系和标签齐全后，仍需检查哪一处记忆无法支持继续工作。

### 6. Memory Health Check：把缺口路由为补证或人工复核

- **要回答的问题：** 如何检查项目记忆是否足以支持下一步，而不把检查器写成自动事实裁判？
- **本书健康检查：** 输入为注入的节点、关系、状态、来源指针、复核时间和后继动作；输出只可分类为 `ready_for_followup`、`needs_evidence` 或 `needs_review`，并列出原因码。
- **检查维度：** 稳定节点是否有来源指针和复核时间；被替代节点是否指向替代节点；下一步是否有明确对象；关键关系是否有目标；同步范围是否已声明边界。
- **最小证据：** 以缺来源、过期复核、悬空链接、无后继动作和完整受限网络各给一项虚构输入与保守结果。
- **失败分支：** 内容真伪、来源本身是否权威、链接目标是否可访问、Agent 是否有读取权、外部系统状态或真实 vault 扫描均在检查器职责外；遇到这些问题必须输出限制或人工复核。
- **预期验证：** 读者能写出“健康检查通过只代表给定字段结构完整，不代表章节事实正确”的报告限制。
- **过渡：** 当记忆要跨设备或跨责任人传播时，健康还需包含同步前的停止条件。

### 7. Synchronization Boundary：同步前先记录冲突出口与责任

- **要回答的问题：** 为什么同步渠道的存在不能替代协作规则、备份责任和冲突处理？
- **来源事实：** REF-105 仅用于说明 Obsidian Sync 的私有跨设备同步服务语境，以及与其他云存储同时使用前备份以避免冲突的官方提醒。
- **本书 Synchronization Boundary：** 记录候选渠道、覆盖的目录或节点、负责角色、变更入口、冲突停止条件、备份责任与人工决策出口；它不是任何同步服务、云盘或 Git 的配置。
- **最小证据：** 为虚构的“只在两台受控设备间传递章节记忆”写出一个未启用的边界记录，明确 `channel: undecided` 时不得把协作范围扩展为已同步。
- **失败分支：** 多个同步渠道、备份未知、所有者未知、冲突不能被安全解释、需要真实账户／设备或写入权限时，停止同步尝试并建立 Escalation Record 或人工任务。
- **预期验证：** 读者能解释同步边界的完成条件是责任和停止出口清楚，而不是应用界面显示某个状态。
- **过渡：** 下一节把前述结构检查收束成无副作用的教学评估器。

### 8. 最小示例：纯内存项目记忆图评估器

- **要回答的问题：** 怎样让记忆健康规则具有可运行、可反驳的最小接口，而不读取真实 vault？
- **示例边界：** 后续暂定 `assessProjectMemoryGraph(graph)` 只检查注入对象；不得读取 Markdown 文件、打开 Obsidian、执行同步、访问网络、云盘、Git、账户、设备、文件系统、子进程、插件或 Agent 工具。
- **计划返回：** 完整教学图可返回 `ready_for_followup / project_memory_graph_ready / implement_in_isolated_example / executionPerformed: false`；缺稳定标识、来源、复核时间、后继动作、关系目标或同步边界时返回 `stopped`／`needs_review` 与原因码。
- **计划测试：** 完整图、稳定结论缺来源、过期复核、悬空链接、`superseded` 无替代节点、标签冒充身份、未定义同步范围和输入声称执行外部同步。
- **预期验证：** Example Implementation 阶段先记录模块缺失红灯，再以实际 Node 测试和演示确认纯函数；提纲阶段不把接口、命令或预期输出写成已运行事实。
- **过渡：** 图示需要同时展示节点关系、健康检查与不能越过的同步／人工复核出口。

### 9. 图示与完整教学案例：从章节证据网到可交接下一步

- **要回答的问题：** 一张图和一个案例如何同时表达知识关系、生命周期与保守停止？
- **图示内容：** `chapter-31` 连接 `research-brief`、`source-card`、`test-evidence-plan`、`diagram-review`、`fact-check` 与 `open-question`；节点经 Link Contract 汇入 Memory Health Check，完整结构进入 `ready_for_followup`，缺证据／过期／关系悬空进入 `needs_review`，同步请求另行进入 Synchronization Boundary。
- **关键箭头解释：** 没有“文件存在 → 事实正确”“标签 → 完整依赖图”“健康通过 → 自动写入”“同步渠道 → 已授权协作”的箭头。图中所有节点都是本书虚构教学输入，不表示仓库、Obsidian 或外部系统已被读取。
- **案例组织：** 用一张表按“节点 → 主要归属 → 状态 → 关系 → 最小证据 → 当前不能主张的事实”串起虚构章节证据网；将一个未决问题指向第 32 章的 Bug Investigation 主题，但不声称任何失败调查已经发生。
- **最小证据：** 每个 `stable` 结论应有来源卡、复核时间和下一步／替代关系；所有跨工具关系均标为相对 Markdown 链接或明确的 Obsidian 特定形式。
- **预期验证：** 读者能在节点缺 `reviewed_at` 时说明为什么图仍可浏览、但不得成为无需复核的接力输入。
- **过渡：** 若要把教学图接入实际项目，需要逐项增加读取、协作和安全控制。

### 10. 逐步增强、总结与后续连接

- **要回答的问题：** 从纯内存模型走向真实项目记忆时，每新增一种能力为什么必须同时增加控制？
- **渐进表：**

| 新需求 | 必须新增的控制 | 升级触发 | 本章为何不实现 |
| --- | --- | --- | --- |
| 读取真实 Markdown 项目材料 | 获批路径、只读范围、敏感信息规则、读取记录与新鲜度检查。 | 要主张当前项目内容。 | 示例不含文件读取接口。 |
| 创建或迁移 vault 属性 | 备份、schema 迁移计划、字段冲突检查、预览与回读。 | 要改变真实笔记结构。 | 本章字段只是教学模型。 |
| 使用 Obsidian 特定链接或插件 | 写作当日产品／插件核验、跨工具回退、权限与数据边界。 | 可移植 Markdown 不足。 | 本章不打开 Obsidian 或安装插件。 |
| 跨设备或多人同步 | 已选渠道、负责人、冲突处理、备份和人工升级。 | 记忆需要离开单一受控位置。 | Synchronization Boundary 不执行同步。 |
| 让 Agent 提议更新项目记忆 | 最小写权限、变更预览、来源复核、人工批准、回读和审计。 | 要从阅读升级为写入。 | 节点／健康检查不授予工具权限。 |

- **总结回收：** 可持续项目记忆不是“更多笔记”，而是让路径、节点、关系、生命周期、健康检查和同步责任各自只回答自身能证明的问题。
- **练习：**
  1. 为一个“依赖升级决策”写出 Memory Node、生命周期状态、来源关系和下一步，指出哪些字段仍不能证明结论正确。
  2. 为一个 `superseded` 节点设计替代关系，并写出悬空替代链接应如何被健康检查路由。
  3. 比较相对 Markdown 链接与 Wikilink 在跨工具场景中可主张的最小能力。
  4. 为一个计划同步给同事的记忆目录写出 Synchronization Boundary，并列出必须人工决定的冲突。
- **后续连接：** 第 34 章把单个可复用能力扩展为团队级 Skill Library 的登记、质量、版本和弃用；第 37 章再从案例抽象出 Memory 与 Skill 的设计模式；第 43 至 45 章把项目记忆应用到技术书生产与跨工具交接。
