# 第 29 章 Research Brief：AI 软件工程师工作流

## 要解决的问题

“让 Agent 改一个功能”常被缩写成生成代码。但可交付的软件变更还要求把需求范围、代码探索、变更计划、验证、文档影响和审查对象连成能被下一位维护者检查的证据链。本章研究的不是某个 IDE 或 Agent 产品的能力，而是一个软件变更从候选需求到**可请求审查**之前必须显式表达的工件。

本章的核心问题是：如何使 Agent 交付的是可判断的变更包，而不是一段无法归属、无法验证也无法审查的代码建议？

## 读者、前置与章节边界

- **目标读者：** 已具备基本代码阅读能力、想把 AI 输出纳入日常工程流程的开发、测试和技术管理读者。
- **前置章节：** 第 09 章 Planning、第 10 章 Workflow、第 17 章 Evaluation、第 25 章仓库级规则、第 27 章 Git/worktree/代码审查，以及第 28 章最小 Harness。
- **本章负责：** 需求澄清、探索证据、受限计划、验证计划、文档决定和审查包之间的接口。
- **本章不负责：** Flutter 设备测试（第 30 章）、pytest/Playwright 分层测试（第 31 章）、故障根因分析与修复（第 32 章）、真实 Git/CI/浏览器/模型/权限系统的运行。

## 论证路线

1. 用一个“新增摘要字段但范围不断膨胀”的场景说明代码片段不能构成交付。
2. 将工程工作拆成六个可审查工件，而不是按某个产品按钮组织。
3. 区分“计划了验证”“实际运行了验证”和“审查或合并已经批准”。
4. 以纯内存评估器验证交付包是否齐全、路径是否越界、文档影响是否已决定。
5. 说明真实执行时需要额外的仓库、环境、权限、测试输出、diff 和人类审查证据。

## 计划示例与验证

计划创建 `examples/agent/software-change-delivery-assessment.mjs`：

- 输入为注入的六类对象，不接受文件系统、子进程、网络、Git 或 Tool 回调。
- 输出为 `ready_for_review` 或带原因码的 `stopped`，并固定 `executionPerformed: false`。
- 先创建测试、实际运行并记录 `ERR_MODULE_NOT_FOUND` 红灯；再创建实现。
- 绿色验证使用 `node --test examples/agent/software-change-delivery-assessment.test.mjs`；演示命令为 `node examples/agent/software-change-delivery-assessment.mjs`。

预期覆盖：完整交付包、缺少 Change Brief、缺验收条件、探索不足、计划越界、缺验证计划、文档影响未决定和审查包不完整。测试不能证明真实需求正确、路径存在、Git diff 正确、测试命令可运行、文档已更新或任何人已经审查。
