# 第 33 章 Research Brief：Obsidian 项目记忆系统

## 要解决的工程问题

长周期项目里的记忆不应只是散落的聊天摘要：读者需要找到某章为何这样设计、事实来自哪里、哪些结论仍待核验，以及下一位人类或 Agent 应从何处继续。若只把 Markdown 文件不断堆入文件夹，内容虽未丢失，却难以按关系、状态和责任重新装配。本章研究如何以 Obsidian 的 vault、属性和链接作为受限的文件组织背景，再提出一套人类与 Agent 共读的项目记忆层（Project Memory Layer）。

这里的重点不是配置某个 Obsidian vault，也不是让 Agent 自动写入知识库；重点是把“可浏览”拆成可定位节点、可追溯关系、明确生命周期和可检查的健康条件。人类可在 Obsidian 中查看这些文件，Agent 可在获得明确文件权限的任务中读取或提出更新候选；两种读取者都不能由文件存在本身获得执行、同步或写入授权。

## 读者问题、范围与非范围

| 读者问题 | 本章研究的回答 | 本章不回答 |
| --- | --- | --- |
| 怎样让章节、来源与审查结论不互相断开？ | 为每个记忆节点声明稳定标识、用途、生命周期状态、来源或结论链接，并用链接契约（Link Contract）限定边的含义。 | Obsidian 或 Markdown 自动保证关系正确、事实新鲜或审查已通过。 |
| 为什么不只用文件夹和标签？ | 文件夹表达主要归属；属性表达结构化筛选字段；链接表达具体关系；标签只保留为粗粒度主题或生命周期辅助。 | 任何一种分类机制能替代其他机制，或标签树天然等于项目本体。 |
| 怎样避免项目记忆变成“什么都有但什么也找不到”的笔记堆？ | 提出记忆健康检查（Memory Health Check）：检查无所有者、无状态、无来源、无后继动作、失效链接和过期节点。 | 检查清单已扫描真实 vault、修复链接、删除笔记或判定内容真伪。 |
| 多设备或多人更新时怎样控制风险？ | 以同步边界（Synchronization Boundary）记录选定同步方式、所有者、冲突处理入口与备份责任；未定义时停止扩展协作范围。 | 已配置 Obsidian Sync、云盘、Git、共享权限、冲突解决或备份。 |

## 已核验的一手资料

| 本地键 | 来源明确表达的内容 | 允许用途 | 不可外推 |
| --- | --- | --- | --- |
| CH33-REF-01 | Obsidian 将笔记保存为 vault 中的 Markdown 纯文本文件；vault 是本地文件系统中的文件夹，且应用会刷新外部更改。 | 将普通 Markdown 与本地文件夹作为项目记忆可读表面的产品背景。 | 外部编辑必然无冲突、任何 Agent 已获文件访问权，或仓库已被 Obsidian 打开。 |
| CH33-REF-02 | Obsidian 属性（Properties）可保存文本、链接、日期、复选框、数字等结构化数据；属性位于文件顶部的 YAML，且同名属性在 vault 中使用同一类型。 | 讨论用于状态、负责人、复核日期和关联链接的结构化字段。 | 某套属性 schema 已被产品强制、YAML 本身保证语义正确，或批量迁移已完成。 |
| CH33-REF-03 | Obsidian 支持 Wikilink 与 Markdown 内部链接；重命名文件时可自动更新 vault 内链接，也可关闭该行为。 | 比较可移植的 Markdown 链接与 Obsidian 内链接，并要求在项目中选择一种稳定规则。 | 任何外部 Markdown 渲染器都理解 Wikilink／块引用，或重命名一定保留所有跨工具关系。 |
| CH33-REF-04 | 标签用于帮助查找笔记；YAML 的 `tags` 属性使用列表，嵌套标签可帮助筛选相关标签。 | 将标签限定为粗粒度检索入口或生命周期辅助。 | 标签层级就是权威目录、知识图或访问控制。 |
| CH33-REF-05 | Obsidian Sync 是跨设备私有同步笔记的附加服务；官方提醒与其他云存储同时使用时应先备份以避免同步冲突。 | 说明同步是需要单独选择与核验的产品能力，并为本书同步边界提供风险背景。 | 当前项目已启用 Sync、具备团队协作资格、已备份，或任何同步方案都能安全合并内容。 |

## 来源事实与本书工程模型

下列工件是本书为案例提出的工程模型，不是 Obsidian 的预置目录、数据模型、插件功能或同步协议。

| 工件或边界 | 要解决的问题 | 关键限制 |
| --- | --- | --- |
| 项目记忆层（Project Memory Layer） | 为人类和 Agent 提供同一组可读、可定位、可审查的 Markdown 项目材料。 | 同读不等于同一权限、自动加载、自动写入或共享理解。 |
| 记忆节点（Memory Node） | 用稳定标识、用途、状态、所有者、复核日期和指针描述一条项目记忆。 | 节点存在不证明内容正确、新鲜或已经落实。 |
| 链接契约（Link Contract） | 为“来源支持”“审查覆盖”“替代”“阻塞”“下一步”等关系指定方向、含义与可追溯目标。 | 链接可点击不证明被链接内容仍存在、正确或可访问。 |
| 生命周期记录（Lifecycle Record） | 将笔记标为收集、核验中、稳定、已替代、归档或待删除，并保留下一步。 | 状态字段不自动触发迁移、删除、通知或审批。 |
| 记忆健康检查（Memory Health Check） | 以节点、关系、状态、来源、责任和新鲜度为输入，保守地路由为可继续、补证或人工复核。 | 不扫描真实 vault，不修改文件，不判定事实，也不执行同步。 |
| 同步边界（Synchronization Boundary） | 在跨设备或协作前记录同步渠道、覆盖范围、负责人、冲突出口与备份责任。 | 不是 Obsidian Sync、Git、云盘的配置，也不授予访问或写入权限。 |

## 章节论证与案例计划

教学案例使用一个虚构的“第 31 章登录测试证据”记忆网：`chapter-31` 节点链接到 Research Brief、来源卡、测试证据计划、图示审查、事实核验和下一章的未决问题。案例中的结论、责任人和日期均为教学输入，不代表本仓已有 Obsidian 数据、测试记录或团队决定。

First Draft 应把记忆设计拆成以下可审查的层次：

1. **Vault 与目录归属：** 用文件夹安排章节、来源、决策、审查和归档的主要归属，避免以“知识图”替代文件路径与所有权。
2. **属性与状态：** 对每个记忆节点明确 `id`、`kind`、`status`、`owner`、`reviewed_at` 与 `next_action` 等教学字段；字段名和枚举值是本书约定，不归因于 Obsidian。
3. **链接与可移植性：** 为需要跨工具读取的核心关系优先约定 Markdown 相对链接；若展示 Wikilink，必须标注其 Obsidian 特定性与渲染边界。
4. **标签与检索：** 标签只回答“这是什么主题或处于什么粗粒度阶段”，不承载唯一身份、权限或完整依赖图。
5. **生命周期与同步：** 先决定何时稳定、何时替代、何时归档；跨设备或多人协作前，先写出同步边界与冲突停止条件。

后续图示应以“章节节点 → 来源与审查节点 → 状态／下一步 → 记忆健康检查”的关系图表达链接契约，并显式画出从健康检查到 `needs_review` 的保守出口。图中不得把 Obsidian 应用、同步服务或 Agent 写成已运行的外部系统。

后续最小示例应只评估注入的记忆图对象，例如判断每个稳定结论是否同时具有来源指针、复核日期和后继动作；返回结果必须包含 `executionPerformed: false`。Example Implementation 阶段才决定是否建立纯内存实现与 Node 测试；本阶段没有创建 vault、启动 Obsidian、读取本地笔记、安装插件、执行同步、访问云盘或调用任何 Agent 工具。

## 风险、非范围与后续核验

- 不在本章记录真实 vault 路径、设备、账户、订阅、同步日志、备份、插件、第三方云盘、Git 远端或任何个人项目笔记。
- 不把内部链接的重命名更新外推到仓库外链接、所有渲染器、块引用、附件、Git 历史或人工语义关系。
