# 第 29 章详细提纲：AI 软件工程师工作流

## 写作契约

### 本章要完成的学习目标

读者完成本章后应能：

1. 将一句软件需求转写为包含目标、验收条件、非目标和允许路径的变更简报（Change Brief）。
2. 说明探索记录、实现计划、验证计划、文档决定和审查包为何不能互相替代。
3. 用交付材料是否完整，而非模型的自述，判断何时才可以请求审查。
4. 为范围扩大、探索不足、验证缺失、文档影响未决定和审查材料不完整设置可解释的停止出口。
5. 指出真实仓库变更仍须另行产生哪些环境、命令、差异、权限与人工审查证据。

### 读者、前置与明确边界

- **读者：** 能阅读 JavaScript 对象和基本测试，想把 AI 输出纳入日常变更流程的开发、测试与技术管理读者。
- **前置：** 第 09 章的任务拆解、第 10 章的状态、第 17 章的证据与评估、第 27 章的 Git/worktree/审查边界，以及第 28 章的最小准入器。
- **本章负责：** 软件变更从需求澄清到“可请求审查”之间的工件接口与停止规则。
- **本章不负责：** 真实 Git 或 Pull Request 操作（第 27 章）、Flutter 登录交付（第 30 章）、pytest/Playwright 分层测试（第 31 章）、失败根因与修复闭环（第 32 章），以及任何真实仓库、CI、浏览器、网络、凭证或权限系统的执行。

## 章节叙事与逐节蓝图

### 1. 从“代码建议”到“可审查的变更交付”

- **要回答的问题：** 为什么一段看起来合理的补丁不能构成软件交付？
- **场景输入：** 维护者提出“为报告摘要增加格式化字段”，模型可以立即生成代码，却还不知道范围、既有行为、文档影响和验证方式。
- **需要建立的区分：** 引用 CH29-REF-01 时只说明其对 workflow/Agent 的分类与工程建议；随后转入本书判断：交付需要可观察、可追溯的工件，不是模型输出更长的解释。
- **最小证据：** 用两列对比“代码片段”与“变更交付包”分别能回答、不能回答的问题；不展示真实补丁或仓库输出。
- **预期验证：** 读者能指出“代码看起来正确”无法证明验收条件、路径范围、文档同步或审查材料已经存在。
- **过渡：** 引出教学案例，以一项小字段改动使六类工件具有具体对象。

### 2. 场景：给报告摘要增加一个格式化字段

- **要回答的问题：** 怎样把模糊需求收缩为可判断的变更边界？
- **教学案例：** 使用虚构的 `src/report/summary.mjs`、`tests/report/summary.test.mjs` 与 `README.md`；目标是新增格式化字段，非目标是认证、存储和无关清理。
- **需要建立的区分：** `allowedPaths` 是本书模型中的范围声明，不是路径存在性、文件写权限或 Git 跟踪状态。
- **最小证据：** 展示 Change Brief 表格：目标、两项验收条件、非目标和允许路径。表格后单列“当前不知道什么”，防止把假设装作探索结果。
- **预期验证：** 读者能判断一个计划若纳入 `src/auth/session.mjs`，应先停止并澄清范围，而非悄悄扩大任务。
- **过渡：** 案例中的每个信息将被分配给一种独立工件。

### 3. 六类工件：每个问题只由一种材料回答

- **要回答的问题：** 为什么不能用一段自然语言计划同时承担需求、探索、验证、文档和审查责任？
- **核心内容：** 按以下顺序定义六类本书工程工件，并为每项给出“回答的问题 / 最小字段 / 不回答的问题”。

| 工件 | 最小字段 | 回答的问题 | 明确不回答 |
| --- | --- | --- | --- |
| Change Brief | `id`、`objective`、`acceptanceCriteria`、`nonGoals`、`allowedPaths` | 要改什么，什么算满足，范围在哪里？ | 代码已改或需求已批准。 |
| Exploration Record | `inspectedPaths`、`relevantBehavior`、`unknowns` | 看过什么，已知行为是什么，仍缺什么？ | 所有仓库行为都已被理解。 |
| Implementation Plan | `steps`、`plannedPaths` | 准备按什么次序修改哪些声明内路径？ | 路径存在、可写或已改。 |
| Verification Plan | `command`、`expectedEvidence`、`externalEffects` | 后续要运行什么、看什么证据、效果边界是什么？ | 命令已经运行或验证通过。 |
| Documentation Decision | `impact`、`paths`、`rationale` | 文档要更新还是不更新，为什么？ | 文档已经同步。 |
| Review Package | `changedPaths`、`diffSummary`、`evidenceStatus`、`reviewState` | 审查者应看什么、当前证据处于什么状态？ | 已有真实 diff、批准或合并。 |

- **最小证据：** 对每个对象只展示字段形状和一个案例值；避免把真实文件、Issue、用户或命令输出伪装为案例事实。
- **预期验证：** 让读者将“README 是否需要改”归属为 Documentation Decision，而不是 Implementation Plan 或 Review Package 的隐含事项。
- **过渡：** 六类工件必须共同接受范围和缺失检查，不能按任意顺序拼接为“完成”。

### 4. 交付门：从材料齐全到保守停止

- **要回答的问题：** 怎样把“再想一想”转换为可检查、可交接的停止规则？
- **核心内容：** 定义本书的 Software Change Delivery Gate：先检查 Change Brief 和验收条件，再检查探索、实现范围、验证计划、文档决定和审查包。
- **停止路径：** 为 `missing_change_brief`、`missing_acceptance_criteria`、`missing_exploration_record`、`scope_expansion_detected`、`missing_implementation_plan`、`missing_verification_plan`、`documentation_impact_unknown`、`missing_review_package` 和 `review_scope_mismatch` 各给一句面向维护者的补充动作。
- **最小证据：** 放置“输入缺失 → 原因码 → 应补何种工件”的表，而非用模型置信度、重试次数或泛化风险分数取代原因。
- **预期验证：** 读者可对“探索记录没有相关行为”说明为何必须停止，且知道停止不等于实现或系统失败。
- **过渡：** 交付门只能输出一个中间状态；下一节拆开它与执行、审查、合并的关系。

### 5. 拆开计划、执行、审查与合并的证据强度

- **要回答的问题：** 为什么 `ready_for_review` 不能被理解为“代码已经改好”？
- **核心内容：** 用四行证据表区分“已计划验证”“已运行验证”“可请求审查”“已批准/已合并”。所有本章评估器输出均固定为 `executionPerformed: false`。
- **来源事实：** CH29-REF-02 只支持 `git diff` 的比较语义；CH29-REF-03 只支持 GitHub 平台的三种评审状态。正文需说明真实 diff 和真实平台评审都在本章示例之外。
- **最小证据：** 在 Review Package 中展示 `evidenceStatus: 'planned'` 与 `reviewState: 'ready_for_review'`，并注明它们只是注入的教学输入。
- **预期验证：** 读者能识别两种错误推理：从验证计划推出测试通过，以及从审查包推出 PR 已批准。
- **过渡：** 在不执行动作的前提下，下一节以纯函数检验交付门的接受和停止行为。

### 6. 最小示例：纯内存的软件变更交付包评估器

- **要回答的问题：** 如何让交付门的规则有可运行、可反驳的最小实现？
- **示例边界：** `assessSoftwareChangeDelivery` 只接收六类注入对象；不得传入文件读取器、Shell 回调、Git 客户端、网络客户端、测试运行器或写入器。
- **接口叙述：** 输入通过时返回 `ready_for_review / software_change_package_ready / request_review / executionPerformed: false`；输入不足时返回 `stopped / 原因码 / stop`。
- **计划测试：** 一条完整交付包路径，九条缺失或范围不一致路径；断言只检查公开返回值，不检查内部辅助函数。
- **来源与验证：** CH29-REF-04 仅用于解释 Node 测试入口；本章后续实现阶段才记录实际的红灯、绿灯和演示输出。提纲阶段不把命令字符串写为已执行证据。
- **过渡：** 准入器证明的是输入分类，仍需说明何时、怎样增加真实读取、测试和变更动作。

### 7. 图示：从 Change Brief 到独立审查的断点

- **要回答的问题：** 交付门在哪些地方必须停止，哪些步骤不能被图省略？
- **图示内容：** 六类工件并行汇入 Delivery Gate；齐全时输出 `ready_for_review`，缺失或越界时输出 `stopped`；`ready_for_review` 之后依次是本章不执行的真实实现与验证、运行证据与实际 diff、独立审查与合并决定。
- **关键箭头解释：** 明确没有从 Change Brief 直接通向“代码已改”，也没有从 `ready_for_review` 直接通向“已合并”；“运行证据不能倒推准备状态”的虚线必须在正文解释。
- **工件与验收：** 正文 Mermaid 块必须与 `diagrams/mermaid/chapter-29-software-change-delivery-loop.mmd` 一致；导出图、替代描述与读图结论在 Diagram Review 阶段核验。
- **过渡：** 图把边界展开为流程；下一节把它收回到一个完整的教学交付包表格。

### 8. 完整教学案例：从变更简报到审查包

- **要回答的问题：** 六类工件在同一个小变更中怎样互相约束？
- **案例组织：** 用一张横向表按“工件 → 案例内容 → 交付门检查 → 当前不能声称的事实”串起全部输入。
- **关键决策：**
  1. 先写验收与非目标，再允许探索和计划。
  2. 计划路径与审查包路径都必须是 `allowedPaths` 的子集。
  3. 文档影响必须是 `update` 或 `none`，`unknown` 必须停止。
  4. 验证命令只保留为计划，直到受控环境实际执行并采集退出码、输出和必要观察。
- **最小证据：** 案例中各路径、命令和差异摘要均标为虚构输入；不展示真实仓库名、提交号、分支、Issue、CI 记录或用户数据。
- **预期验证：** 读者能把一个“测试通过”的自述拆回具体证据缺口，而不是接受整体陈述。
- **过渡：** 案例获得交付门准入后，仍要在真实工程中逐项增加环境和控制。

### 9. 逐步增强：何时离开纯函数

- **要回答的问题：** 交付包要接入真实工程时，每新增一种风险应增加什么控制？
- **渐进表：**

| 新需求 | 新增控制 | 升级触发 | 本章为何不实现 |
| --- | --- | --- | --- |
| 读取真实仓库 | 只读范围、读取记录、敏感文件规则 | 必须确认当前行为 | 示例没有文件读取接口。 |
| 运行项目测试 | 环境快照、受控命令、超时、退出码与输出保留 | 要从计划验证升级到实际验证 | 示例不执行 `command`。 |
| 修改文件 | 环境契约、最小写权限、预览、回读与回滚 | 动作会产生外部效果 | `allowedPaths` 不是权限。 |
| 创建真实 diff 或提交 | 工作树状态、身份、分支和审查策略 | 要交付真实变化 | `diffSummary` 不是 Git 输出。 |
| 验证 UI 或设备 | 目标设备/浏览器、交互、前后观察与报告 | 改动影响用户可见行为 | 留给第 30、31 章。 |
| 修复失败 | 最小复现、可证伪假设、回归与复盘 | 已有失败观察 | 留给第 32 章。 |

- **预期验证：** 每个升级触发都应能说明“为什么原有纯函数证据不够”，而不是只因项目规模变大就增加框架。
- **过渡：** 最后一节收束可迁移原则与后续章节的责任边界。

### 10. 总结、练习与后续连接

- **要回答的问题：** 读者应带走什么，而不误把本章模型当作生产流程？
- **总结回收：** 交付包是让需求、范围、验证、文档和审查具备明确接口的教学模型；`ready_for_review` 是保守的中间状态。
- **练习：**
  1. 为“公开 API 字段重命名”写出 Change Brief，并列出至少两个非目标。
  2. 给一份包含越界路径的 Implementation Plan 写出正确停止码和补充动作。
  3. 比较“验证计划已声明”和“测试已执行”的最小证据差异。
- **后续连接：** 第 30 章把交付包落到 Flutter 登录与测试报告；第 31 章展开 API/UI 测试层次；第 32 章在失败发生后转入最小复现、假设与回归测试。
