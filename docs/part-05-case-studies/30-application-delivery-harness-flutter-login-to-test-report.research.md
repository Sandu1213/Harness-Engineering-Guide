# 第 30 章 Research Brief：应用交付 Harness：Flutter 登录到测试报告

## 要解决的工程问题

一个 Agent 收到“完成登录功能”的任务时，最容易只产生界面代码或一段测试建议。移动功能交付还需要回答：需求是否可验收、登录状态是否能区分输入错误与请求失败、测试观察来自哪一层、设备或模拟器是否真的被运行，以及报告到底能主张什么。本章把这些问题串成一个**交付计划准入**案例，而不是声称实现了某个真实 Flutter 应用。

## 读者问题与范围

| 读者问题 | 本章回答 | 本章不回答 |
| --- | --- | --- |
| “登录页面能显示”是否等于功能完成？ | 不等于；需求、状态、测试矩阵、观察和报告必须分层。 | 真实认证协议、后端安全设计或产品发布。 |
| 怎样覆盖成功、输入校验失败和网络失败？ | 用三条可观察场景和分层测试计划组织证据。 | 某个 SDK、网络库或状态管理库的最佳选型。 |
| 何时可以写“已在设备上通过”？ | 只有保存了对应环境、命令、观察和限制时。 | 本章没有运行真机、模拟器、浏览器或 CI。 |

## 本书工程模型

下列工件均是本书的交付 Harness 模型，不是 Flutter 官方 schema、合规框架或生产运行记录。

| 工件 | 解决的问题 | 关键边界 |
| --- | --- | --- |
| Delivery Contract | “登录功能完成”具体指什么。 | 不保证需求正确或获得发布批准。 |
| State Model | 输入校验、提交、成功和网络失败如何区分。 | 不代表任何真实状态管理库。 |
| Test Matrix | 哪一层检查哪种可观察结果。 | 计划不等于执行结果。 |
| Observation Record | 某次测试实际看到了什么。 | 缺失记录时不能推断为通过。 |
| Report Contract | 报告必须附带场景、层级、观察、结论和限制。 | 报告模板不会自动产生可信证据。 |

## 教学案例与验证设计

教学案例为一个虚构的移动登录表单，只有三条场景：成功登录、空输入触发校验错误、已提交后得到网络失败。示例不构建 Dart/Flutter 工程，不存储密码，不发起请求，不启动设备；它只审查由测试注入的交付计划对象能否进入“隔离实现”阶段。

计划交付物：

- 原创正式正文、Research Brief、详细 Outline、参考资料、事实核验和示例计划；
- 一张从 Delivery Contract 到报告边界的 Mermaid 图；
- 一个 Node 纯内存准入器与 8 项测试，先记录模块缺失红灯，再实现绿色路径；
- Technical、Example、Diagram、Language 与 Final Review 记录。

## 风险与写作护栏

- 不能把 Flutter 官方文档中的演示命令写成本仓执行结果。
- 不将“计划有 integration 测试”写成“用户已经完成端到端流程”。
- 不使用真实凭证、用户数据、网络地址、应用包、设备名称、构建号或测试报告截图。
- 将第 25 章的浏览器交互证据、第 31 章的 pytest/Playwright 分层测试、第 32 章的失败诊断保留给相邻章节；本章只讲移动功能的交付链。
