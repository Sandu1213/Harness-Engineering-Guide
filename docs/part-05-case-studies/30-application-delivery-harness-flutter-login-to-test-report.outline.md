# 第 30 章详细 Outline：应用交付 Harness：Flutter 登录到测试报告

## 写作契约

### 本章要完成的学习目标

读者完成本章后应能：

1. 将“完成登录功能”收缩为带有可观察验收、数据限制和非目标的交付契约（Delivery Contract）。
2. 用状态模型（State Model）区分输入校验失败、提交中、认证成功和网络失败，而不把这些名称当作 Flutter 框架 API。
3. 说明 unit、widget、integration 三类测试各自能提供什么有限证据，及其为什么不能互相替代。
4. 将测试矩阵（Test Matrix）、观察记录（Observation Record）和报告契约（Report Contract）分开，以免把计划或“绿色”自述写成环境执行事实。
5. 在纯内存准入器输出 `ready` 时，列出仍需真实 Flutter 项目、设备/模拟器、命令、观察和人工决定才能主张的事项。

### 读者、前置与明确边界

- **读者：** 能读 JavaScript 对象与基本测试，且希望把移动端功能交付拆成可审查步骤的开发、测试与技术管理读者。
- **前置：** 第 17 章的评估和证据、第 25 章的交互前后观察、第 28 章的最小 Harness，以及第 29 章的软件变更交付包。
- **本章负责：** 将一个虚构 Flutter 登录功能的需求、状态、测试计划、观察和报告组织为可准入的移动交付计划。
- **本章不负责：** 真实 Flutter/Dart 编码、构建、签名、安装、设备或模拟器控制、后端认证、账户安全、浏览器 E2E、CI、测试云、发布和故障根因分析。

## 章节叙事与逐节蓝图

### 1. 从“登录页面能显示”到可交付的登录功能

- **要回答的问题：** 为什么显示一个登录表单不能单独证明功能已经完成？
- **场景输入：** 虚构团队要求交付一个登录入口；验收至少区分输入为空、提交后网络失败和认证成功三条场景，且不得使用真实凭证或账户。
- **核心论证：** 将“页面能显示”“状态已建模”“测试已计划”“环境已观察”“报告可主张”排成递增证据强度，而不是把它们合并为一个“完成”标签。
- **最小证据：** 使用两列表比较“UI 片段能回答的问题”与“交付契约必须补充的问题”；案例字段均为虚构，不展示真实账号、地址或包名。
- **预期验证：** 读者能指出缺少网络失败场景、数据策略或验收条件时，不应直接进入实现。
- **过渡：** 首先把需求和状态写成独立工件，避免测试和报告为缺失的行为定义兜底。

### 2. 交付契约与状态模型：先定义要观察什么

- **要回答的问题：** 怎样在写组件或测试前说清“登录”应有哪些可观察结果？
- **交付契约：** 定义 `id`、`objective`、`acceptanceCriteria`、`nonGoals`、`dataPolicy` 和 `allowedArtifacts`；其中 `dataPolicy: 'no-real-credentials'` 是教学约束，不是安全系统配置。
- **状态模型：** 使用 `idle`、`validating`、`submitting`、`authenticated`、`validation_error`、`network_error`。每个状态说明进入条件、可观察结果和不应倒推的事实；它们不是任何 Flutter 状态管理库的固定名称。
- **来源事实：** REF-093 仅说明 Flutter 表单示例如何用 `Form`、`GlobalKey` 与 `validate()` 检查输入；本章将输入校验放入三场景之一，是原创案例设计。
- **最小证据：** 一张“状态 → 场景 → 可见/可记录观察 → 不证明什么”的表。例如 `validation_error` 只能说明注入计划要求独立错误分支，不能说明真实表单已渲染。
- **预期验证：** 读者能在“只有 authenticated 与 failed”的状态计划中找出输入校验和网络问题被错误折叠的位置。
- **过渡：** 状态说明了要观察的行为，下一节说明不同测试层应如何贡献这些观察。

### 3. 分层测试：每种证据只回答它能回答的问题

- **要回答的问题：** unit、widget、integration 测试为何不能只选一种？
- **来源事实：** REF-092 将 unit、widget、integration 分别限制为逻辑单元、单一 widget、完整应用或大部分应用的测试；REF-094 说明集成测试资料中的交互、绑定和设备/模拟器运行语境。
- **本书测试矩阵：**

| 层级 | 教学对象 | 可观察问题 | 必须另行补足 | 本章不声称 |
| --- | --- | --- | --- | --- |
| unit | 状态转换或输入规则 | 空输入是否分类为 `validation_error`。 | 组件交互和环境行为。 | Flutter 测试已经运行。 |
| widget | 单个表单的显示与交互计划 | 错误提示和提交控制应观察什么。 | 真实网络、设备和完整应用协作。 | 某个 widget 已渲染。 |
| integration | 应用的大段协作与目标环境计划 | 从输入到结果需保存哪些交互观察。 | 测试报告、CI、发布或认证安全。 | 设备/模拟器已经执行。 |

- **最小证据：** 通过矩阵展示计划值 `executionTarget: 'planned'`，说明层级出现不等于运行发生。
- **预期验证：** 读者能解释“一个 Node 单元测试通过”为什么不能替代 Flutter widget 或集成测试。
- **过渡：** 测试矩阵只声明未来需要什么；下一节再区分计划、执行观察和最终报告。

### 4. 计划、观察与报告：不要把“绿了”写成事实

- **要回答的问题：** 什么证据允许报告“已执行”，什么只能报告“已计划”？
- **核心工件：** Test Matrix 声明场景、层级和预期观察；Observation Record 绑定任务、场景、来源、时刻、观察和限制；Report Contract 规定报告必须给出 `scenario`、`layer`、`observation`、`verdict`、`limitation` 和关联标识。
- **证据强度表：** 对比 `claimState: 'planned'`、`observed`、`verified` 和“需要人工升级”四类句子；其中后三类不是本章示例可自动生成的状态。
- **最小证据：** 以报告字段缺少 `observation` 的输入为例，说明准入器必须停止，而不是推测运行通过。
- **预期验证：** 读者能发现“unit、widget、integration 都写在表里”不等于任何一个层级有实际输出。
- **过渡：** 在动作之前，所有计划需要一起通过一次受限的交付准入检查。

### 5. 应用交付门：把缺失材料路由为停止或批准请求

- **要回答的问题：** 如何让任务缺口变成明确的补充动作，而不是泛泛的“再检查一下”？
- **核心内容：** 定义本书的 Flutter Login Delivery Gate，按顺序检查任务合同、数据策略、六个状态、三条场景、三层测试、报告字段、任务关联和环境执行批准。
- **停止/升级路径：**

| 缺口 | 返回状态 | 面向维护者的下一步 | 不能推断 |
| --- | --- | --- | --- |
| 任务合同缺失 | `stopped / missing_task_contract` | 补目标、验收和非目标。 | 实现需求无效。 |
| 真实凭证策略 | `stopped / credential_policy_violation` | 收缩为无真实凭证的教学输入。 | 凭证已经泄露或安全。 |
| 状态或场景不全 | `stopped / missing_required_state` 或 `missing_test_scenario` | 补独立状态和可观察场景。 | 测试已失败。 |
| 报告没有观察 | `stopped / report_claim_not_observed` | 记录真实观察或保留为计划。 | 环境执行曾发生。 |
| 请求环境执行 | `requires_approval / environment_execution_not_approved` | 交给具有具体环境授权的人确认。 | 设备、权限或运行条件存在。 |

- **最小证据：** 原因码—补充工件表，而不是置信度分数、模型解释或虚构测试日志。
- **预期验证：** 读者能说明 `requires_approval` 与 `ready` 的差异：前者不允许例外环境操作，后者也只允许进入隔离实现阶段。
- **过渡：** 下一节把这组准入规则实现为无副作用的最小函数。

### 6. 最小示例：纯内存 Flutter 登录交付计划准入器

- **要回答的问题：** 怎样让移动交付计划的停止规则可运行、可反驳，同时不伪造移动环境？
- **示例边界：** `assessFlutterLoginDelivery(deliveryPackage)` 只检查注入对象；不得启动 `flutter`、Dart、设备、模拟器、浏览器、网络、认证服务、文件、CI、密钥或真实报告。
- **接口叙述：** 完整输入返回 `ready / flutter_login_delivery_plan_ready / implement_in_isolated_example / executionPerformed: false`；不完整输入返回 `stopped`，环境请求返回 `requires_approval`。
- **计划测试：** 一条完整交付计划路径、任务合同缺失、凭证策略违规、状态缺失、场景缺失、报告声称执行、环境执行未批准和报告关联错误；断言仅检查公开返回合同。
- **来源与验证：** REF-090 仅支持 Node 测试入口；Example Implementation 阶段才记录 `ERR_MODULE_NOT_FOUND` 红灯、8 项绿灯和演示输出，Outline 不将它们提前描述为本轮运行结果。
- **过渡：** 准入器只分类输入，图示应继续保留从计划到真实环境之间不可跳过的证据断点。

### 7. 图示：从交付契约到报告结论的不可跳过断点

- **要回答的问题：** 在一张图里怎样防止“有计划”被读成“已通过”？
- **图示内容：** Delivery Contract、State Model、Test Matrix 和 Report Contract 汇入 Delivery Gate；计划完整时指向 `ready` 与隔离实现，环境执行请求指向批准出口；真实 Flutter 测试、目标观察和报告结论位于本章示例之外。
- **关键箭头解释：** 无“Test Matrix → 已执行”的箭头；无“`ready` → 报告已通过”的箭头；Observation Record 只能由实际运行后产生，不能倒推生成。
- **工件与验收：** 正文 Mermaid 块与 `diagrams/mermaid/chapter-30-flutter-login-delivery-chain.mmd` 必须逐字一致；导出 SVG/PNG、替代描述和可读性在 Diagram Review 阶段验证。
- **过渡：** 图保留了断点，下一节用完整虚构案例串起所有工件。

### 8. 完整教学案例：三场景登录计划如何进入审查

- **要回答的问题：** 同一交付计划中，需求、状态、测试和报告怎样彼此约束？
- **案例组织：** 以“成功认证、空输入、提交后网络失败”三场景为行，以目标状态、测试层级、需要观察、报告限制为列。
- **关键决策：**
  1. 先将 `validation_error` 与 `network_error` 分开，避免用单一失败状态掩盖不同恢复路径。
  2. 在无真实凭证策略下只引用虚构场景标识，而不在计划、测试或报告中出现账号或 token。
  3. 仅将实际观察关联到一次具名环境执行；不存在 Observation Record 时，Report Contract 必须保留 `planned` 或停止。
  4. 设备/模拟器验证必须先有特定环境批准，不能因集成测试计划存在而默认获得授权。
- **最小证据：** 每个路径都写明“计划证明什么 / 需要什么观察 / 当前不能说什么”；不展示截图、设备名、构建号、网络地址或测试云结果。
- **预期验证：** 读者能拒绝把“成功路径已经在矩阵中”写成“用户能够登录”。
- **过渡：** 若要让教学计划成为真实工程流程，必须按风险一次增加一种环境控制。

### 9. 逐步增强：何时离开纯内存计划

- **要回答的问题：** 从准入器走向真实 Flutter 交付，每一步为什么要增加新的控制？
- **渐进表：**

| 新需求 | 新增控制 | 升级触发 | 本章为何不实现 |
| --- | --- | --- | --- |
| 创建 Flutter 项目 | 明确 SDK、项目来源和本地读写边界。 | 需要检查真实 Dart/Widget 行为。 | 示例没有文件或进程接口。 |
| 运行 unit/widget 测试 | 记录命令、版本、退出码、输出与未覆盖范围。 | 要从测试计划升级到实际测试。 | `executionPerformed` 固定为 `false`。 |
| 运行设备/模拟器集成测试 | 目标环境、授权、前后观察、失败工件与清理。 | 要主张用户可见交互。 | 本章不连接设备或模拟器。 |
| 使用认证服务 | 安全设计、无密钥日志、后端契约和最小权限。 | 要触及真实身份或网络。 | 案例禁止真实凭证和请求。 |
| 生成测试报告 | 不可伪造的 Observation Record、关联、结论限制和人工审核。 | 要向团队发布执行结论。 | Report Contract 只是字段约束。 |
| 诊断失败 | 最小复现、可证伪假设、回归测试和复盘。 | 已收到真实失败观察。 | 留给第 32 章。 |

- **预期验证：** 每一行都应指出原始纯函数为何不足，而不是以“规模变大”为理由添加框架。
- **过渡：** 最后一节回收移动交付中的证据边界，并连接后续测试和诊断章节。

### 10. 总结、练习与后续连接

- **要回答的问题：** 读者应带走哪些规则，而不把交付计划当作真实移动验证？
- **总结回收：** 交付契约定义目标，状态模型定义差异，测试矩阵定义将来要看的证据，观察记录限制执行结论，报告契约限制语言强度；`ready` 仅是隔离实现准备状态。
- **练习：**
  1. 为“登录按钮被禁用”写出一条验收条件、一条非目标和对应状态观察。
  2. 给一份缺少 `network_error` 的测试矩阵选择正确停止码，并说明为何不能将它合并进输入校验错误。
  3. 给出一条只有 `planned` 的报告，列出把它升级为“已在设备上观察到”的最小额外证据。
- **后续连接：** 第 31 章展开 API 与浏览器自动化的测试层次；第 32 章在真实失败观察出现后处理最小复现、假设和回归。第 29 章负责通用软件变更交付，不重复本章的移动场景证据模型。
